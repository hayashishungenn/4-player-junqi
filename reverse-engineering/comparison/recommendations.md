# 四国军棋可借鉴技术方案

## 1. 边界

- 只借鉴**设计思路**：引擎进程化、难度阶梯、评分标签、提示成本、复盘数据、训练闭环。
- 不复制任何商业代码、素材、商标、音效、私有接口。
- 四国军棋规则、搜索、估值、界面全部使用主工程自有实现。
- 本文不修改主工程 AI 引擎；只给出接口与阶段方案，待逆向阶段验收后再落地。

## 2. 总体架构建议

```text
┌──────────────────────────────┐
│ 客户端/UI（自有）             │
│  对局、提示、复盘、训练        │
└──────────▲───────────────────┘
           │ 本地协议（JSON/文本）
┌──────────┴───────────────────┐
│ 引擎服务（自有，独立进程/线程）│
│  ├ 对弈引擎（搜索 + GNN 估值） │
│  ├ 分析引擎（评分/候选/胜率）  │
│  └ 开局库/定式库               │
└──────────────────────────────┘
```

借鉴点：

- **引擎与 UI 解耦**：像 Pikafish/KataGo 一样通过协议通信，UI 不直接调用搜索内部。
- **对弈与分析分离**：两个引擎实例，复盘不污染对弈置换表；四国军棋可用同一模型、不同预算。
- **可替换引擎**：协议稳定后，弱 AI（启发式）与强 AI（GNN）可互换。

## 3. 协议建议（自有设计，不照搬 UCI/GTP 文本）

建议 JSON 消息，便于携带四人座位、队伍、隐藏信息：

```json
{"cmd":"newgame","seats":4,"teams":[[0,2],[1,3]],"rules":"siguo-v1"}
{"cmd":"setposition","fen":"...","seat":1,"visible":{"0":[...],"1":[...]}}
{"cmd":"go","seat":1,"budget":{"type":"depth|nodes|time","value":8}}
{"cmd":"analyze","seat":1,"multipv":5,"budget":{"type":"time","value":1000}}
{"cmd":"stop"}
```

引擎输出：

```json
{"type":"info","depth":8,"score":{"team":0,"cp":35},"wdl":[520,380,100],"pv":["..."]}
{"type":"bestmove","move":"...","confidence":0.72}
```

四国军棋特有字段：

- `seat`：0–3。
- `teams`：队伍映射。
- `visible`：当前玩家可见信息（不完全信息）。
- `belief`：可选，引擎内部的信念状态摘要，供分析/调试。

## 4. 难度系统

采用 game-01 的 13 档思路，但参数按四国军棋重标定：

| 档位 | 目标 | 搜索预算 | 候选采样 | 安全阈值 |
|---:|---|---|---|---|
| 0–1 | 新手 | 深度 1–2 / 极少节点 | 前 5 随机 | 禁止送大子/暴露军旗 |
| 2–4 | 入门 | 深度 3–4 | 前 3 随机 | 禁止明显亏子 |
| 5–6 | 中级 | 深度 5–6 | 前 2 随机 | 保留 |
| 7–8 | 高级 | 深度 7–8 | 前 1–2 | 保留 |
| 9–10 | 大师 | 深度 9–11 | 前 1 | 保留 |
| 11–12 | 顶尖 | 深度 12+ / GNN 满预算 | 前 1 | 保留 |

实现要点（直接借鉴 game-01）：

1. **同档多配置**：进入对局随机抽一套并整局固定，制造风格差异。
2. **候选随机采样**：在 MultiPV 前 N 条中随机；若最佳着法与采样着法的期望值差超过阈值，强制回最佳。
3. **分阶段配置**：开局 N 步用开局库/定式，之后切换搜索配置。
4. **不使用“降低网络精度”**：那会让 AI 显得呆滞；用预算与采样控制。

## 5. 搜索与估值

四国军棋与象棋/围棋的根本差异：

- 不完全信息（棋子暗置、军旗位置未知）。
- 四人两队，存在配合与背叛风险（队友意图）。
- 随机性（部分规则含随机布阵/翻棋）。

建议：

1. **信念状态搜索**：对未知棋子做采样/确定化（determinization），多次采样取期望；不要假装全知。
2. **团队价值**：估值输出“本队胜率/期望”，而不是单人胜负；队友动作作为联合动作处理。
3. **GNN 估值**：用主工程现有 GNN 对局面图（棋子、位置、可见性、队伍）编码；输出价值 + 候选策略。
4. **搜索**：在信念采样上做 MCTS/PUCT 或深度受限的 Alpha-Beta（视主工程引擎），保留置换表、Zobrist、开/定式库。
5. **安全约束**：低难度必须过滤“送军旗/送大子”的着法，避免拟人化变成送分。

## 6. 评分与复盘

借鉴 game-01 的标签体系，但增加“信息不足”维度：

| 标签 | 条件 |
|---|---|
| Best | 与实际着法一致或期望损失 < 阈值 |
| Good | 损失小于动态阈值 |
| Book | 命中开局/定式库 |
| Inaccuracy | 轻度损失 |
| Mistake | 明显损失 |
| Blunder | 重大损失 |
| Missed | 存在必胜/必和手段未走 |
| Risky-OK | 信息不足下的合理冒险（新增） |
| Unknown | 无法判定 |

阈值建议：

- 均势：绝对期望损失阈值（如 50 厘兵等价单位）。
- 大优/大劣：相对百分比阈值，避免“优势下苛责”。
- 团队局面：以“本队胜率变化”为主，个人得失为辅。
- 每次评分附带 `confidence`（采样方差/可见信息量），低置信度不轻易标 Blunder。

复盘数据：

```json
{
  "moves": [...],
  "perMove": [{"move":"...","score":35,"wdl":[520,380,100],"label":"Good","conf":0.81}],
  "curve": {"winrate":[...],"score":[...]},
  "belief": [{"seat":1,"known":[...],"unknown":[...]}]
}
```

## 7. 提示

- 输出 top-k 候选 + 风险等级 + 简短理由（“可试”“有风险”“唯一解”）。
- 次数限制：训练/关卡消耗提示次数；普通对局可配置。
- 防重复扣费：同一回合重复点击不扣。
- 分析预算：500–1000ms 快速模式，用户可切“深度分析”。

## 8. 棋谱与回放

- 内部格式：自有 JSON（版本号、规则版本、座位、队伍、布阵、着法、可见性快照、分析数组）。
- 导出格式：自有文本/JSON；如需兼容，可提供 SGF 风格或 PGN 风格导出，但不依赖商业格式。
- 回放：逐步前进/后退、跳转、分支试下、推荐箭头、评分图标、胜率曲线。
- 版本兼容：记录 `rulesVersion`，规则变更时可拒绝加载或迁移。

## 9. 训练闭环

| 模块 | 内容 | 借鉴 |
|---|---|---|
| 开局布阵 | 给定阵型，练习应对 | game-01 初始局面选择 |
| 记牌/推理 | 根据已出棋子推断暗子 | 四国特有 |
| 配合信号 | 队友意图识别与响应 | 四国特有 |
| 残局收束 | 少量棋子的必胜/必和 | game-01 残局题库 |
| 复盘课 | 从自己的对局生成错题 | game-01 逐手评分 |
| 进度 | 段位/ELO、关卡解锁 | game-01 生涯模式 |

## 10. 实施阶段

### P0（逆向验收后）

1. 定义引擎协议与记录格式（本文第 3、8 节）。
2. 封装现有搜索引擎为独立引擎服务；保持行为不变。
3. 记录对局与逐手期望值（先不做评分）。

### P1

1. 接入分析模式：MultiPV、胜率、置信度。
2. 实现评分标签与阈值。
3. 复盘 UI：逐手导航、曲线、箭头。

### P2

1. 难度 13 档与候选采样。
2. 开局/定式库。
3. 提示成本与训练关卡。
4. 用自我对弈/GNN 更新估值，回归测试难度曲线。

## 11. 验收指标

- 引擎协议可被独立进程调用，单步延迟在预算内。
- 同一局记录可无损回放，评分可复算。
- 低难度不出现“送军旗/送大子”的明显错误（抽样对局人工检查）。
- 高难度在固定测试集上胜率显著高于低难度（难度单调性）。
- 复盘标签与人工标注一致率达到约定阈值。

## 12. 明确不做

- 不复制 Pikafish/KataGo 代码或网络到主工程（仅借鉴协议与产品设计）。
- 不伪造服务器端算法；四国军棋 AI 全部本地/自有。
- 不在证据不足时大改现有 AI 引擎；先做协议与记录层。
