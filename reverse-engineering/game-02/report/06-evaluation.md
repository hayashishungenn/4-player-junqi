# 报告 06：局面估值分析（game-02）

## 1. 估值来源

《Just Go》的局面估值完全来自 KataGo 的神经网络，业务层不包含手写棋力评估代码（二进制缺失，但 GTP 输出足以证明估值由引擎给出）。 [已验证]

## 2. 网络

- 模型：`kata1-b40c256-s10032125184-d2445637108.bin.gz`
  - `b40c256`：40 个残差块、256 通道。
  - `s10032125184`：训练步数约 100.3 亿。
  - `d2445637108`：训练数据/日期标识。
- 输入尺寸：日志显示同时初始化 19×19 与 9×9 缓冲，说明同一网络支持多棋盘尺寸。
- 后端：Eigen CPU，4 线程；未使用 GPU。

## 3. 输出头

从 `Player.log` 的 `katago:info` 行可确认：

| 输出 | 字段 | 含义 |
|---|---|---|
| 策略先验 | `prior` | 该着法的先验概率 |
| 胜率 | `winrate` | 当前局面胜率（0–1） |
| 目差 | `scoreLead` / `scoreMean` | 期望领先目数 |
| 波动 | `scoreStdev` | 目差标准差 |
| 归属 | `ownership`（`kata-analyze ... ownership true`） | 每个交叉点归属概率 |
| 原始网络 | `kata-raw-nn 1` | 直接读取网络输出 |

此外 KataGo 自身日志还输出 `whiteWin 0.168739`、`varTimeLeft 9.228`、`noResult 0.000908` 等诊断值（`Player.log` 中 `katago:white*`、`katago:var*`、`katago:no*`）。

## 4. 业务层如何消费估值

从存档字段可反推：

- `WhiteLeadScores`：每步保存一个 `double` 领先目数（首元素为初始局面，长度 = 手数 + 1）。
- `WhiteWinRates`：每步保存白方胜率，供复盘曲线。

示例 `RecentGames/match_1768530733.sav`：

```text
Moves: 134
WhiteLeadScores: 135 项，如 -1.447, -0.971, -1.878, 3.893, ...
```

说明业务层把引擎的 `scoreLead` 按手记录，形成“逐手形势曲线”。这与 game-01 用 `CentipawnValue` 记录评分的做法同构，只是单位从“厘兵”变为“目”。

## 5. 未发现

- 手写子力/位置表：未发现（业务层不可见，GTP 输出也无此迹象） [有证据支持]
- 传统棋形特征：KataGo 内部使用，业务层不涉及
- 终局/死活库：未发现
- 让子估值：`Handicap` 字段存在，具体处理未知

- `scoreLead` 与界面“目数”的换算是否直接使用，未验证。
- 是否对胜率做了平滑/映射（如显示百分比）。
